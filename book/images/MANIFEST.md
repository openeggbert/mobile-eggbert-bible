## Known gaps / honesty notes

- Any animation table referenced by `Decor.cpp` that this pipeline could not locate as real numeric data in `Tables.cpp` was skipped rather than guessed — look for `[object] SKIP` lines in `extract_sprites.py`'s console output on a fresh run for the current list (none were skipped as of the last run that produced this file, unless noted per-row above).
- `table_tiplouf` (ObjectType35) is declared in `Tables.cpp` with only 3 real elements even though `Decor.cpp:8619` indexes it modulo 7 — a genuine array-bounds inconsistency in the original engine. The `object-035-small-plouf.png` sheet renders only the 3 real elements; frames 3-6 are not fabricated to paper over the gap.
- `ObjectType32`/`ObjectType33` ("blupih"/"blupit" clones) never receive an explicit `PixmapChannel` assignment inside `Decor::MoveObjectStepIcon` (unlike every other patrol-creature type in the same function). Their sheets are rendered on `PixmapChannel::Blupi` because every icon value in `table_blupih_*`/`table_blupit_*` (61-70, 237-250) falls inside `blupi.png`'s addressable range and the table names mirror the Blupi asset family — this is a reasoned inference from the data, not a located, explicit assignment; flagged here rather than presented as fully confirmed.
- `blupi1.png` is not used by any `table_blupi`-driven `BlupiAction` sequence. The only place it is genuinely used is `ObjectType201/202/203` (avatar costume skins, icons 257-262, static per skin) and the first 30 frames of `ObjectType38`'s electric-arc effect (`object-038-electric-arc.png`, the one sheet in this catalog that draws from it).
